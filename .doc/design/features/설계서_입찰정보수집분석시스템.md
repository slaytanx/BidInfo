# 입찰정보 수집·분류·문서 분석 시스템

최신 업데이트: 2026-10-31

## 처리 흐름

공개 목록 조회 → 수집원별 중복 검사 → 제목 사전 분류 → 상세 분류 → 첨부 수집 → 문서 추출 → 분야 확인 → JSON 분석 → SQLite 저장 → 화면 표시 순으로 처리합니다. 국민은행은 실제 `formPage`의 `viewPage` 값으로 페이징하며 농협 전체 게시판과 농협정보시스템은 각각의 POST 목록 양식을 사용합니다. 날짜 없는 행을 임의로 오늘 공고로 처리하지 않습니다.

분야·세부 항목·업무를 각각 복수 선택하고 같은 축 안에서는 OR, 선택한 축 사이에서는 AND로 확인합니다. 기본값은 관련성이 확인된 공고만 첨부를 수집하며 불확실한 건은 판단 보류로 저장합니다. 규칙으로 명백한 비IT 공고만 조기에 제외하며 로컬 분류가 불확실하면 첨부를 확인합니다. 목록에는 반복 감지와 최대 페이지 제한을 두고 그 상태를 실행 결과에 표시합니다. 공개 목록·상세·첨부 접근 상태를 별도로 기록합니다. 외부 전자구매 시스템은 원본 확인 대상으로 남깁니다.

## 동시 실행과 재사용

수집 작업과 문서·분석 작업은 각각 최대 2건을 처리합니다. 프로세스 내 로컬 모델 호출은 1건, OpenRouter 호출은 2건으로 제한합니다. SQLite 저장과 Streamlit 갱신은 주 실행 흐름에서 처리합니다. 서버별 요청 간격은 최소 0.3초이며 모든 요청에 연결·응답 제한 시간과 제한된 재시도를 적용합니다.

문서 캐시는 파일 내용 해시·추출기 버전·OCR 설정으로 식별합니다. 실패·부분 성공은 캐시하지 않습니다. 분석 캐시는 프롬프트·전체 입력·평가 키워드·프롬프트 버전·공급자·모델을 포함합니다. 폴백 결과를 원래 모델 결과로 재사용하지 않습니다. 긴 문서는 9,000자 구간을 모두 분석하고 순차 병합하며 근거는 중복을 제거해 보존합니다.

판단 보류는 공고 정보만 저장하고 첨부·상세 분석을 하지 않습니다. 수동 확정 건은 별도 선택 실행에서 해당 ID만 수집하며 일반 수집은 수동 대기열을 소모하지 않습니다. 수동 분류는 자동 갱신으로 덮어쓰지 않습니다. 완료한 공고는 다운로드 전에 건너뜁니다. 실패한 작업은 다시 시도하며 사용자가 첨부 새로 확인을 선택하면 완료한 공고도 재수집합니다. 평가 기준이나 모델 변경 후 기존 공고 재분석은 별도 버튼과 CLI 옵션을 사용합니다.

## 모델과 결과 인터페이스

기본 혼합 모드는 `gemma4:e4b-mlx` 분류와 `deepseek/deepseek-v4-flash-0731` 분석을 사용합니다. 로컬 모드와 최종 폴백은 `gemma4:26b-mlx`입니다. OpenRouter 모드의 사전 분류는 로컬 규칙으로 수행하고 클라우드 상세 분석을 사용합니다.

`analyze_bid_with_ollama`의 기존 함수 이름과 주요 인자를 유지합니다. 결과에는 기존 요약·점수·마감·제출·자격 필드에 태그, 근거, 예산, 수행기간, 평가배점, 유의사항, 권장 목차, 분석 상태, 사용 모델과 캐시 식별자가 추가됩니다. JSON 형식·타입·점수 범위를 검사합니다. 사실 필드에 원문에서 확인할 수 있는 인용이 없으면 `확인 불가`로 처리합니다. 권장 목차는 제안 항목으로 구분합니다.

비용은 실행별 `RunBudget`에서 가격 조회·예약·정산합니다. UTF-8 입력 바이트 수와 최대 출력 토큰으로 보수적으로 예약하며 동시 요청·재시도도 포함합니다. 알 수 없는 과금은 예약액을 사용합니다. 가격을 확인할 수 없거나 예산이 부족하면 로컬로 전환합니다. 앱 집계는 해당 실행의 텍스트 호출이며 외부 계정 전체 지출 한도는 아닙니다.

## 문서 처리

LLM이 표 구조를 읽을 수 있도록 표는 Markdown 표, 엑셀은 CSV로 넘깁니다. HWP는 FileHeader의 압축·암호화 플래그와 BodyText의 문단 텍스트 레코드를 처리하고, 표(TABLE)·셀(LIST_HEADER) 레코드의 행·열 주소로 표를 Markdown 표로 복원합니다(병합 셀은 첫 칸에만 내용). HWPX는 문단과 표를 원문 순서대로 읽고 표를 Markdown 표로 바꿉니다. PDF는 `pymupdf4llm`으로 페이지별 Markdown(표 포함)을 만들고, 텍스트가 부족한 페이지에만 Tesseract 한국어·영어 OCR을 적용합니다. DOCX·PPTX·HTML은 `pandoc`(gfm), XLSX·XLS는 `pandas` 시트별 CSV로 변환합니다. 구형 DOC는 DOCX 변환이 필요하다는 사유로 실패 처리합니다. TXT와 확장자가 잘못된 지원 문서도 실제 형식을 확인합니다.

파일별 결과에는 성공·부분 성공·실패, 처리 방식, 오류와 페이지/섹션 근거가 포함됩니다. 다른 공고 폴더를 제목 유사성으로 대신 읽지 않습니다. ZIP은 경로 이탈·심볼릭 링크·크기·압축률·중첩 깊이를 제한합니다. 암호화·손상·미지원 파일은 실패 원인을 남기며 추출 실패를 분석 성공으로 처리하지 않습니다.

## 저장과 호환

상위 분야·세부 항목·업무 사전은 `taxonomy`에 저장하고 관리합니다. 공고에는 `solution_tags`, `work_tags`, `legacy_tags`, `classification_status`, `manual_classification`, `notice_text`를 추가했습니다. [분류 설계](설계서_분야솔루션업무분류.md)에 키워드와 수동 검토 흐름을 기록했습니다.

기존 공고 테이블에 `source_key`, `source_id`, `tags`, `classification_reason`, `extraction_status`, `extraction_details`, `analysis_status`, `analysis_model`, `analysis_key`, `evidence`, `download_status`를 추가합니다. JSON 목록과 객체는 TEXT로 저장합니다. `bid_id`는 수집원과 원래 ID를 결합하며 수집원별 ID에 고유 인덱스를 둡니다. 원래 ID만 전달한 기존 상태 변경·삭제 호출은 한 공고로 식별될 때 지원하고 충돌하면 오류를 반환합니다.

기존 공고의 요약·찜·진행 상태를 보존하며 실패한 재분석으로 기존 정상 요약을 지우지 않습니다. 기존 API 키 설정은 로컬 비밀 파일로 이전하고 공고 DB에서 제거합니다. 환경변수·로컬 `.env`·`.local_secrets.json`을 지원하며 비밀 파일은 Git 제외와 `0600` 권한을 적용합니다.

R2는 기본 비활성화이며 자동 DB 다운로드를 수행하지 않습니다. 명시적 업로드는 SQLite 일관된 스냅샷과 첨부를 사용하고 백업·캐시·비밀 파일을 제외합니다. 활성화 시 기존 관리자 상태 변경·삭제의 동기화 동작은 유지합니다.

## 검증

기존 `unittest` 환경을 사용합니다. 합성 문서·격리 DB·모의 API로 분류, 사전 제외, 중복, 문서 추출, OCR, 캐시, 긴 문서 후반부, 비용 제한과 상태 보존을 검증합니다. Streamlit AppTest는 합성 공고의 화면·필터 동작을 확인합니다. 실제 문서는 별도 읽기·원문 비교 검증 자료로 구분합니다. 클라우드 모델 실측은 유효한 API 키가 있는 경우에만 실행하며 미연결을 성공으로 표시하지 않습니다.
