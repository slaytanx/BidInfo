# 스키마 및 데이터 모델 명세서 (Schema & Data Model Specification)

최신 업데이트: 2026-11-09

본 문서는 입찰정보 수집·분석 시스템의 데이터베이스 테이블 스키마, 식별자 생성 규칙, JSON 직렬화 구조, 캐시 무효화 원리 및 리포트 내보내기 데이터 모델의 세부 동작 규격을 정의합니다.

---

## 1. 데이터베이스 구성 (SQLite)

* **파일 경로**: `data/bids_history.db`
* **엔진**: SQLite 3 (WAL 모드, `PRAGMA journal_mode=WAL;`, `PRAGMA busy_timeout=5000;`)
* **연결 관리**: `db.get_db_connection()` 컨텍스트 매니저 기반 30초 타임아웃 보장
* **캐시 무효화 핑거프린트 (`db_stamp()`)**:
  UI 성능 최적화를 위해 메인 DB 파일(`data/bids_history.db`)과 WAL 파일(`data/bids_history.db-wal`)의 `(mtime_ns, size)` 튜플을 결합 추적합니다. DB 쓰기 발생 시 스탬프가 변경되어 Streamlit의 `@st.cache_data`가 즉각 무효화됩니다.

## 2. 테이블 스키마 명세

### 2.1. `bids` (입찰 공고 테이블)

입찰 공고의 원본 메타데이터, 분류 결과, 첨부파일 추출 현황, AI 분석 결과 및 사용자 상태를 단일 레코드로 통합 관리합니다.

| 컬럼명 | 데이터 타입 | 기본값 | 제약조건 | 설명 |
| :--- | :--- | :--- | :--- | :--- |
| `bid_id` | TEXT | - | **PRIMARY KEY** | 정규화된 고유 공고 ID (`<source_key>:<raw_id>`) |
| `source_key` | TEXT | `''` | - | 수집원 축약 식별자 (예: `kb`, `nh`, `nhit`, `shinds`, `hanati` 등) |
| `source_id` | TEXT | `''` | - | 원본 사이트의 원시 게시글 번호 또는 식별 키 |
| `site_name` | TEXT | `'미지정'` | - | 수집원 사이트 표기명 (예: `KB국민은행`, `신한DS 사업공시`) |
| `num` | TEXT | - | - | 원본 게시판의 노출 순번 |
| `org` | TEXT | - | - | 발주 기관명 (공고 제목에서 자동 파싱된 금융 계열사명 포함) |

| `reg_date` | TEXT | - | - | 공고 등록일 (`YYYY-MM-DD` 표준 포맷) |
| `deadline` | TEXT | `'확인 불가'` | - | 제안서 제출 마감 일시 (추출 문자열 원문) |
| `submit_type` | TEXT | `'확인 불가'` | - | 제출 방식 (전자입찰, 방문제출, 우편 등) |

| `qualifications` | TEXT | `'확인 불가'` | - | 입찰 참가 자격 요건 |

| `fit_score` | INTEGER | `0` | 0~100 | AI 비즈니스 적합도 점수 |
| `fit_reason` | TEXT | - | - | 적합도 산정 근거 |
| `tags` | TEXT | `'[]'` | JSON Array | 1축: 대분야 태그 (`['보안', '클라우드']`) |
| `solution_tags` | TEXT | `'[]'` | JSON Array | 2축: 세부 솔루션 태그 (`['방화벽', 'EDR']`) |
| `work_tags` | TEXT | `'[]'` | JSON Array | 3축: 업무 유형 태그 (`['구축', '유지보수']`) |
| `legacy_tags` | TEXT | `'[]'` | JSON Array | 마이그레이션 호환용 레거시 태그 |
| `classification_status`| TEXT | `'자동'` | - | 분류 확정 상태 (`'자동'`, `'수동 분류'`, `'수집 대기'`, `'수집 제외'`, `'판단 보류'`) |
| `classification_reason`| TEXT | `''` | - | 키워드 매칭 또는 LLM 분류 근거 문자열 |
| `manual_classification`| TEXT | `'{}'` | JSON Object | 사용자가 수동 수정한 분류 값 (자동 덮어쓰기 방지) |
| `extraction_status` | TEXT | `'미확인'` | - | 첨부파일 텍스트 추출 상태 (`'성공'`, `'부분 성공'`, `'실패'`, `'미확인'`, `'생략'`) |

| `analysis_key` | TEXT | `''` | - | 분석 캐시 키 (`SHA-256`) |
| `evidence` | TEXT | `'[]'` | JSON Array | 사실 추출 근거 인용문 및 위치 (`[{field, quote, location}]`) |
| `download_status` | TEXT | `'미확인'` | - | 첨부파일 다운로드 상태 (`'성공'`, `'실패'`, `'생략'`, `'미확인'`) |
| `notice_text` | TEXT | `''` | - | 웹 공고 본문 텍스트 원문 (첨부 문서 외 본문 보존용) |
| `folder_path` | TEXT | - | - | 로컬 첨부파일 저장 절대 경로 |
| `origin_url` | TEXT | `''` | - | 원본 입찰 공고 상세 페이지 URL |
| `starred` | INTEGER | `0` | 0 또는 1 | 사용자 찜하기 (관심 공고) 플래그 |
| `status` | TEXT | `'검토중'` | - | 사용자 관리 상태 (`'검토중'`, `'진행예정'`, `'제안완료'`, `'포기'`) |
| `created_at` | TIMESTAMP | CURRENT_TIMESTAMP | - | 레코드 최초 생성 일시 |

#### 인덱스 명세
* **`idx_bid_source`**: `UNIQUE(source_key, source_id)` — 동일 수집원 내 동일 공고 번호의 중복 삽입 방지.

#### 완료 공고 판별 규칙 (`existing_bid_ids`)
다음 3대 상태가 모두 완비된 공고에 한해 수집 완료로 판정하여 중복 네트워크 요청을 스킵합니다:
$$\text{analysis\_status} = \text{'성공'} \land \text{extraction\_status} = \text{'성공'} \land \text{download\_status} = \text{'성공'}$$

#### 분석 실패 시 정상 데이터 보존 메커니즘 (`save_bid`)
재분석 시도시 일시적 네트워크 또는 모델 오류로 `analysis_status='실패'`가 발생하더라도, 기존에 성공적으로 저장되어 있던 주요 필드(`summary`, `fit_score`, `fit_reason`, `deadline`, `submit_type`, `required_docs`, `qualifications`, `evidence`)는 덮어쓰지 않고 보존합니다.

## 3. 식별자 정규화 규칙 (Identifier Specifications)

### 3.1. `source_key(site, url)`
URL의 호스트명 및 사이트 명칭을 분석하여 정규화된 숏키를 산출합니다:
* `nonghyupit.com` 또는 `농협정보시스템` → `'nhit'`
* `kbstar.com` 또는 `국민`/`KB` → `'kb'`
* `nonghyup.com` 또는 `농협` → `'nh'`
* `shinhands.co.kr` 또는 `신한DS` → `'shinds'`
* `shinhan.com` 또는 `신한` → `'shinhan'`
* `hanati.co.kr` 또는 `하나금융티아이` → `'hanati'`
* `kebhana.com` 또는 `하나` → `'hana'`
* 기타 미지정 사이트: `SHA-256(host or site)[:12]`

### 3.2. `canonical_id(raw_id, site, url)`
수집원 간 공고 번호 충돌을 원천 차단하기 위해 접두어를 합성합니다:
$$\text{canonical\_id} = \text{source\_key} + \text{":"} + \text{str(raw\_id)}$$
이미 접두어가 포함되어 있는 경우 재합성하지 않습니다.

## 5. 보고서 내보내기 데이터 모델 명세 (`report_export.py`)

### 5.1. 실무용 스타일 엑셀 내보내기 (`generate_excel_export`)
* **구성**: 단일 시트 (`입찰공고_목록`), 21개 표준 컬럼:
  1. `번호`, 2. `찜`, 3. `진행상태`, 4. `D-Day`, 5. `수집사이트`, 6. `발주기관`, 7. `입찰 공고명`,
  8. `적합도`, 9. `등록일`, 10. `마감일시`, 11. `제출방식`, 12. `추정예산`, 13. `수행기간`,
  14. `분야`, 15. `세부 솔루션`, 16. `업무`, 17. `필수 제출 서류`, 18. `참가 자격 요건`,
  19. `AI 사업 요약`, 20. `적합 사유`, 21. `원본 링크`
* **서식 규칙**:
  * 헤더: 네이비 배경(`1F497D`), 백색 볼드, 테두리, 열 필터 자동 활성화
  * D-Day: 당일(`🔥 D-DAY`) 및 마감 임박(1~3일) 셀은 연분홍 배경(`FFC7CE`)과 붉은 텍스트(`9C0006`)로 시각 강조
  * 적합도 점수: 70점 이상 볼드 강조
  * 원본 링크: `HYPERLINK` 수식 적용, `http://` 및 `https://` 안전 프로토콜 검증 (XSS 방지)
  * 캐싱: `cached_excel(stamp)` 및 `cached_filtered_excel(bid_ids_tuple, stamp)` 기반 바이너리 메모리 캐싱

### 5.2. 제안 검토 보고서 내보내기
* **마크다운 (`generate_bid_review_markdown`)**:
  * 테이블 셀 내부의 파이프(`|`) 및 줄바꿈 문자를 `_safe_md_cell`로 이스케이프하여 마크다운 표 깨짐 방지
  * 사업 개요, 요건 체크리스트, 제안 권장 목차, 원문 근거 인용문 완비
* **HTML (`generate_bid_review_html`)**:
  * 단일 self-contained 파일, A4 세로 인쇄 최적화 스타일시트(`@media print`) 내장

## 6. R2 클라우드 스토리지 파일 구조

Cloudflare R2 버킷(`R2_BUCKET_NAME`, 기본값 `bid-info`) 내 키 네이밍 규격:

```
bid-info/
├── data/
│   ├── <bid_id>/                         # 예: kb:146912/
│   │   ├── [KB국민은행] 제안요청서.pdf
│   │   └── 별첨_기술규격서.xlsx
│   └── bids_history.db                   # 명시적 동기화 시 업로드되는 DB 스냅샷
```
* **제외 대상**: 임시 파일, `cache/`, `scratch/`, `.env`, `.local_secrets.json`은 R2 업로드 대상에서 원천 제외됩니다.
